# amr_person_tracking 작업 흐름 정리 (현재 상태, 미완성 포함)

이 문서는 `docs/vision_pipeline.md`가 설명하는 전체 비전 파이프라인 중 이 저장소가 실제로
구현한 `amr_person_tracking` 패키지 4개 노드(`oakd_detector_node`,
`leg_detector_bridge_node`, `reid_tracking_node`, `predictive_avoidance_node`)가 **지금
시점에 실제로 어떤 순서로, 어떤 조건 분기와 반복을 거쳐, 어디로 통신하며** 동작하는지를
정리한다. 함수명이나 메시지 필드 같은 인터페이스 세부사항이 아니라 "무슨 작업이 어떤 흐름으로
일어나는가"에 초점을 둔다.

**이 문서는 기본 파라미터로 켰을 때의 정상 동작 경로만 다룬다.** 검증해봤지만 이 현장
데이터에서 이득이 없어 꺼둔 기능(외형 ReID 임베딩, 칼만필터/마할라노비스 게이팅, 외형 기반
매칭 거부)과 디버그 시각화 분기(디버그 이미지, FOLLOWING 오버레이, `debug_viewer_node`)는
흐름에서 제외했다 — 그 기능들의 실측 근거와 켜는 법은 `evidence/`의 각 로그와 노드
파라미터 주석에 남겨 뒀다.

주의: launch 파일의 `publish_debug_image` **기본값은 아직 `true`**다(실증 단계라 눈으로
확인하려고 그렇게 뒀다). 즉 launch로 띄우면 이 문서가 제외한 디버그 경로가 실제로는 켜진다.
`debug_viewer_node`는 cv2 창을 띄우므로 headless 환경에서는 예외로 종료한다 — 그런 환경에서는
`publish_debug_image:=false`로 넘길 것.

## 0. 전체 통신 지도 (한눈에 보기)

```
[LiDAR 드라이버]──scan──▶[leg_detector_bridge_node]──leg_detections_3d──▶┐
                                                                         │
                                                                         ▼
[OAK-D 드라이버]──RGB/Depth/CameraInfo──▶[oakd_detector_node]──detections_3d──▶[reid_tracking_node]
[IR/오도메트리]──ir_intensity/odom──────▶        │                                    ▲
                                                 ▼                    (외부, 미연결) webcam/detections_3d
                                          proximity_alert                            │
                                        (근접 안전모드 경보)                          │
                                                                                     ▼
                                                              tracked_detections_3d / target_person_pose
                                                                                     │
                                                                                     ▼
                                                                     [predictive_avoidance_node]
                                                                        │                    │
                                                             predicted_obstacle_points   SetParameters
                                                                        ▼                    ▼
                                                                [Nav2 voxel_layer]   [Nav2 local_costmap]
```

핵심 통신 원칙: **세 검출 소스(웹캠·OAK-D·라이다)가 전부 같은 스키마(3D 위치 + 표준 id
필드)로 `reid_tracking_node`에 모인다.** 하위 노드는 위치가 어디서 왔는지 몰라도 되고,
`reid_tracking_node`만 "지금 이 사람이 어느 소스로 보이고 있는지"를 판단한다.

## 1. `oakd_detector_node` — 근접(1.0~2.5m) 카메라 기반 검출

### 시작 시퀀스 (노드 기동 시 1회)
1. 파라미터 로드 (근접 임계값, 신뢰도 임계값, 동기화 슬롭 등)
2. YOLO-pose 모델 로드 — **실패하면 모델이 없는 채로 노드는 계속 뜨지만, 이후 모든 프레임
   처리를 조용히 건너뛴다** (에러 로그만 남고 크래시하지 않음)
3. tf 버퍼/리스너 준비
4. RGB·Depth 두 압축 이미지 토픽을 **시간 근사 동기화기(ApproximateTimeSynchronizer)**
   에 등록 — 이후 이 둘이 짝지어질 때만 메인 콜백이 불림
5. CameraInfo·Odometry·(옵션)IR 근접센서를 각각 **별도의, 동기화와 무관한** 콜백으로 구독
   시작 — 이 값들은 최신 값만 캐시해뒀다가 메인 콜백이 참조하는 용도
6. 검출 결과 발행자, 근접경보 발행자(마지막 값을 늦게 구독해도 받도록 래치), 진단 발행자,
   (옵션) 디버그 이미지 발행자 준비
7. 1초 주기 진단 타이머 시작 (메인 루프와 독립적으로 계속 반복)

### 메인 루프 — RGB/Depth 동기화 콜백 (한 쌍이 도착할 때마다 반복)
1. **프레임 스킵 분기**: `process_every_n`으로 지정한 배수가 아니면 여기서 종료 (CPU 추론
   부하 조절용 — 처리량과 무관하게 일정 비율만 실제 처리)
2. **모델/CameraInfo 미준비 분기**: YOLO 로드 실패했거나 CameraInfo를 아직 한 번도 못
   받았으면 경고만 남기고 종료 (역투영에 카메라 내부파라미터가 반드시 필요)
3. RGB/Depth 압축 디코딩 — **디코딩 실패 분기**: 각각 실패 시 경고 후 종료
4. 두 프레임의 실제 시간차(슬롭 안에서의 편차)를 계산해뒀다가, 뒤에서 위치 신뢰도(공분산)에
   반영할 재료로 저장
5. YOLO-pose를 **자체 트래킹 모드(persist=True)** 로 추론 — 이 한 번의 추론 호출 안에서
   내부적으로 이전 프레임과 이번 프레임의 사람 상자를 대조해 지속 track_id를 자동으로
   부여한다 (이 track_id 유지력이 라이다 쪽 자체 구현 트래커보다 훨씬 안정적임을 실측 확인 —
   22.74초 동안 라이다 쪽은 트랙 id가 여러 번 바뀐 반면 이쪽은 2번만 바뀜).
   **이때 넘기는 conf는 `tracker_conf_threshold`(기본 0.1)로, 발행 임계(0.3)보다 낮다** —
   저신뢰 검출까지 트래커에 넣어야 TrackTrack/ByteTrack 계열의 2단계 연결(저신뢰 검출을
   기존 트랙에 이어붙여 끊김을 막는 장치)이 살아난다. 발행은 6-a에서 따로 거른다.
6. **검출된 사람 상자 각각에 대해 반복**:
   a. **발행 임계 분기**: `box_conf < conf_threshold`(기본 0.3)이면 트래커 연속성용으로만
      쓰고 발행 대상에서는 제외 (다음 사람으로)
   b. 접지점 **후보들** 산출 — **3단계 분기**: 발목 keypoint가 신뢰도 이상 보이면 좌/우 발목을
      **각각 별개 후보로**(`toe_direct`) / 안 보이면 무릎 keypoint + 박스 하단으로
      보정(`knee_corrected`) / 그것도 없으면 박스 하단 중앙(`angle_only`)
   c. 후보마다 depth 샘플링 후 **방향은 후보들의 중점, 거리는 각 후보 depth의 평균**으로 확정 —
      **무효 분기**: 유효 depth가 하나도 없으면 이 검출은 버림(통계 카운터만 증가).
      좌우 발목 픽셀을 평균한 "중점"에서 depth를 읽으면 걸을 때 그 지점이 두 다리 사이 허공이라
      뒤쪽 벽/바닥이 찍힌다(실측 22.1%). 그렇다고 한쪽 발목만 쓰면 앞발/뒷발이 번갈아 뽑혀
      보폭만큼 진동한다. 그래서 방향과 거리를 분리해서 취한다.
   d. **안전망 분기**: 그렇게 구한 depth가 bbox 안쪽에서 추정한 사람 표면 깊이와
      `depth_consistency_tolerance`(0.4m) 넘게 어긋나면 사람 표면 깊이로 대체하고 등급을 한 단계
      낮춘다(불확실도가 공분산에 반영되도록). c의 방식 도입 후 이 안전망은 실측상 발동하지 않음
   e. 카메라 내부파라미터로 픽셀+depth를 카메라 좌표계 3D 점으로 역투영
   f. tf로 base_link(근접 판정용)와 map(발행용) 두 좌표계로 변환 — **변환 실패 분기**: 둘
      중 하나라도 실패하면 이 검출은 버림 (단, `tf_allow_latest_fallback`이 켜져 있으면
      정확한 시각 대신 최신 tf로 한 번 더 시도)
   g. base_link 기준 거리·방위각 계산 → 지금까지 중 가장 가까운 대상이면 갱신
   h. 화면 잘림(truncation) 비율 계산, 등급별 통계 누적
   i. 이 검출을 표준 3D 검출 목록에 추가 (표준 id 필드에는 `oakd_<track_id>` 저장,
      `pose.covariance[0]`에는 등급+동기 시간차 기반 위치 분산 기록)
7. **근접 안전모드 판정** (검출 루프가 끝난 뒤, 가장 가까운 대상 기준 1회):
   - 대상이 아예 없으면 상태를 idle로만 표시하고 넘어감
   - 이미 근접모드 켜진 상태면 **해제 임계값에 여유(히스테리시스)를 둬서** 판정 (경계에서
     깜빡이지 않도록)
   - 꺼진 상태에서 새로 켜야 할 상황이면, **IR 근접센서 교차확인 분기**: IR 기능이 켜져
     있으면 실제로 그 방향 IR 센서가 반응하는지 한 번 더 확인 후에만 켠다 (IR 데이터가
     없거나 오래됐으면 교차확인을 포기하고 거리 조건만으로 판정 — 안전 기능이 통째로
     죽는 것보다 낫다는 설계)
   - 상태가 실제로 바뀔 때만 근접경보 토픽에 발행 (매 프레임 발행하지 않음)
8. 3D 검출 목록을 `<namespace>/vision/detections_3d`로 발행 → **`reid_tracking_node`가
   구독**

### 독립적으로 계속 도는 보조 루프
- **CameraInfo/Odometry/IR 콜백**: 메인 루프와 비동기로, 도착할 때마다 최신 값만 캐시에
  저장 (메인 루프가 소비)
- **진단 타이머(1초 반복)**: 최근 1초간의 프레임률·검출수·최근접거리·tf실패/뎁스무효
  횟수를 집계해 상태를 4단계(정상/경고/입력끊김/모델없음)로 판정 후
  `<namespace>/diagnostics`로 발행 — 다른 어떤 노드의 처리와도 무관하게 계속 반복

## 2. `leg_detector_bridge_node` — 초근접(<1.0m) 라이다 다리검출

### 시작 시퀀스
1. 파라미터 로드 (클러스터링/곡률/배경필터/트래킹 임계값 전부)
2. 정적배경 저장소(`StaticBackgroundFilter`)와 다리별 칼만 추적기(`LegKalmanTracker`)를
   배경필터 옵션이 켜진 경우에만 생성
3. tf 버퍼/리스너, 검출·마커 발행자 준비
4. LiDAR 스캔 토픽 구독 시작

### 메인 루프 — 스캔 콜백 (스캔 한 장이 들어올 때마다 반복, 보통 초당 여러 번)
1. 극좌표 스캔을 평면 좌표점 목록으로 변환
2. **점들을 인접 거리 기준으로 묶어 클러스터화** (거리가 갑자기 벌어지면 새 클러스터
   시작 — 반복적으로 스캔 전체를 훑음)
3. **각 클러스터를 다리 후보인지 판정 (반복 + 다단 분기)**:
   - 점 개수가 너무 적으면 탈락
   - 첫점-끝점 폭이 다리 굵기 범위를 벗어나면 탈락
   - **곡률 검사 분기(옵션, 기본 켜짐)**: 원형적합이 안 되거나(직선에 가까움), 반지름이
     너무 크거나, 원에 잘 안 붙으면 탈락 — 이 단계가 벽·모서리를 다리로 오검출하던 문제를
     해결한 부분
   - 살아남은 클러스터만 중심점을 다리 후보 좌표로 채택
4. **각 다리 후보를 map 좌표계로 변환** (짝짓기 전에 개별 다리 단위로 변환 — 좌표계 실패
   분기는 OAK-D 노드와 동일한 방식: 실패 시 그 후보만 버림, 옵션에 따라 최신 tf 폴백)
5. **정적배경 필터 분기(옵션, 기본 켜짐)**:
   - 이번에 보인 모든 다리 후보를 다리별 칼만 추적기에 넣어 **매칭(기존 추적 중이던
     물체와의 위치 대조, 반복)** — 매칭되면 그 물체의 속도 추정을 갱신, 안 되면 새 추적
     시작
   - 각 물체가 **"처음 관측된 뒤 누적 나이가 확정 시간 이상이고, 추정 속도가 정지
     임계값 이하"** 조건을 만족하면 그 위치를 정적 배경으로 영구 등록 (한 번 등록되면
     세션 내내 유지 — 사람이 그 물체를 잠깐씩 가려도 나이 계산은 리셋 안 됨, 이게 이전
     설계였던 "그리드 셀 방식"의 실패를 보완한 지점)
   - 등록된 배경 위치 근처의 후보는 이번 프레임 결과에서 제외
6. **짝짓기**: 남은 다리 후보를 거리순으로 그리디하게 두 개씩 묶어 사람 중심점으로
   (짝을 못 찾은 다리는 단독으로도 사람으로 인정하는 옵션이 기본 켜짐 — 한쪽 다리가
   가려진 경우가 흔해서)
7. **이번 콜백에 나온 사람 후보 전체를 한 번에, 기존 트랙에 배타적으로 배정** (한 콜백
   안에서 두 후보가 같은 트랙을 중복으로 차지하지 않도록 전체를 놓고 한 번에 계산)
8. **각 사람 후보에 대해 반복**: 배정된 트랙이 없으면 새 트랙 생성 / 있으면 위치·속도
   갱신 → 검출 메시지와 (옵션) RViz 마커를 만들어 목록에 추가
9. **오래된 트랙 정리** (매 콜백마다, 일정 시간 이상 갱신 안 된 트랙을 반복해서 삭제)
10. 완성된 검출 목록을 `<namespace>/vision/leg_detections_3d`로 발행 →
    **`reid_tracking_node`가 구독**
11. **마커 발행 옵션 분기**: 켜져 있으면 이전 마커를 전부 지우고 새로 그려
    `<namespace>/vision/leg_detections/markers`로 발행 → **RViz가 구독**

## 3. `reid_tracking_node` — 재식별/트래킹 (전체 융합 허브)

이 노드는 **서로 다른 두 개의 독립적인 반복 경로**를 갖는다 — 하나는 웹캠/OAK-D(넓은 범위
카메라 계열) 갱신 경로, 하나는 라이다 다리검출 갱신 경로. 두 경로는 같은 트랙 저장소를
공유하지만 진입 조건과 처리 방식이 다르다.

### 시작 시퀀스
1. 파라미터 로드 (게이팅/블렌딩/락온/스왑/sticky 임계값 전부)
2. 트랙 저장소, 추종 대상 상태, 락온 상태, **dormant 갤러리**를 빈 값으로 초기화
3. 웹캠 검출·OAK-D 검출·라이다 다리검출 세 토픽을 각각 별도 콜백으로 구독 시작
4. 융합 결과·추종 대상 좌표 발행자 준비

### 경로 A — 웹캠/OAK-D 갱신 (두 토픽 공용 처리 로직, 메시지 올 때마다 반복)
1. 이번 메시지의 검출에서 위치를 뽑음
2. **기존 트랙 전체에 배타적으로 한 번에 매칭** — 위치+속도 게이팅으로 후보를 거른 뒤
   Hungarian 전역 최적 배정(`scipy.optimize.linear_sum_assignment`). 예전에는 최근접부터
   그리디로 확정했는데, 지역적으로 최선인 선택이 전체로는 더 나쁜 조합을 만들 수 있어 교체했다
3. **상류 트래커 id 구제**: 상류 id(`oakd_N`)가 예전에 매핑된 트랙이 아직 살아있고 거리
   상한 이내면, **위치 매칭 결과와 무관하게** 그 매핑을 우선 (중복 트랙이 같은 사람의 검출을
   번갈아 차지하며 좌표가 순간이동하던 문제 해결 — 실측 6.4m/s → 3.1m/s)
4. **각 검출에 대해 반복, 매칭 결과별 분기**:
   - 매칭 실패 → **갤러리 부활 분기**: 최근 사라진 신원 중 **마지막으로 보이던 자리에서
     `revival_max_distance`(1.5m) 이내**로 돌아온 것이 있으면 그 신원을 되살림(위치는 새
     관측으로 리셋, 속도는 0에서 재추정 — 공백 동안의 낡은 속도로 외삽하면 안 되므로).
     없으면 새 트랙 생성
   - 매칭 성공 + **이 트랙이 지금 라이다에 락온된 추종 대상인 경우** → 위치를 덮어쓰지
     않음 (두 소스가 매 프레임 번갈아 위치를 쓰면 속도 추정이 왕복운동처럼 튀는 걸 방지) —
     대신 "카메라가 마지막으로 독립적으로 본 위치"만 별도로 기록해둠 (경로 B의 스왑검증이
     나중에 이 값을 씀)
   - 매칭 성공 + 락온 대상이 아닌 경우 → 정상 갱신. **출처가 방금 바뀐 첫 프레임인지
     분기** — 맞으면 위치를 부드럽게 블렌딩, 아니면 그대로 반영
5. **오래된 트랙 정리** (반복, `track_timeout`(3초) 이상 어느 소스로도 안 갱신되면 삭제).
   단 **곧바로 버리지 않고 dormant 갤러리로 옮겨** `dormant_ttl`(30초) 동안 마지막 위치를
   보관한다. 삭제된 게 추종 대상이었다면 "원래 따라가던 신원"으로 기억해둔다
6. **추종 대상 재선정 분기**:
   - `sticky_follow`(기본 켬)이고 **갤러리에서 돌아오길 기다리는 신원이 있으면 → 아무도
     고르지 않는다.** 그동안 추종 좌표는 발행되지 않는다(= "대상 없음"을 침묵으로 표현).
     엉뚱한 사람을 따라가는 것보다 안전하고, `dormant_ttl` 만료가 상한 역할을 한다
   - 기다리는 신원이 없고 현재 대상도 없으면 → 살아있는 트랙 중 가장 먼저 생긴 것을 선택
     (제스처/호출좌표 기반 명시적 지정은 아직 미구현이라 쓰는 자리표시자 정책)
7. 전체 트랙 목록을 `<namespace>/vision/tracked_detections_3d`로, **추종 대상이 있을 때만**
   그 좌표를 `<namespace>/target_person_pose`로 발행.
   `predictive_avoidance_node`가 구독하는 것은 **`tracked_detections_3d` 하나뿐**이다.
   `target_person_pose`는 (디버그 오버레이를 제외하면) 아직 구독자가 없다 - 좌표를 실제
   Nav2 목표로 소비하는 노드는 이 저장소 범위 밖이다.
   각 검출의 `header.stamp`는 배열 헤더가 아니라 **그 트랙이 마지막으로 실제 관측된 시각**이다.
   이번 프레임에 갱신되지 않은 트랙도 `track_timeout` 동안 계속 발행되므로, 하류가 이를 새
   관측으로 오인하지 않도록 구분해 준다.

### 경로 B — 라이다 다리검출 갱신 (라이다 메시지 올 때마다 반복)
1. 이번 메시지의 다리 후보 위치들을 원시 id별로 정리
2. **추종 대상 존재 여부 분기**: 대상 자체가 없으면 신원 매칭이 의미 없으므로 후보
   이력만 갱신하고 종료
3. **락온 상태 분기** (핵심 상태 머신):
   - **락온 중인 경우**:
     - 락온된 원시 id가 이번에 안 보이면 → **유예시간 분기**: 마지막으로 본 지 유예시간
       이내면 그냥 유지(반환), 초과했으면 락온 해제
     - 보이는 경우 → **스왑 의심 검증**: 카메라가 마지막으로 "독립적으로" 본 위치와
       비교(그 값이 너무 오래됐으면 판단 보류) → 편차가 임계값을 넘는 상태가 여러 프레임
       **연속으로** 이어지면(순간적 튐과 구분하기 위함) 스왑 의심으로 락온 해제 →
       유지되면 이 위치로 추종 트랙 갱신
   - **락온 안 된 경우 (재획득 시도)**:
     - 추종 트랙의 마지막 위치+속도를 이번 라이다 메시지 시각까지 시간 정렬(외삽)
     - **게이팅**: 예측 위치와 각 라이다 후보의 거리 중 임계값 이내인 것만 후보로 필터
     - 후보가 여럿이면 위치뿐 아니라 (라이다 후보 자신의 직전 위치로 미분한) 속도
       유사도까지 합쳐 점수화 → 최고점 후보 선정
     - **스트릭 갱신**: 이번에 최고점 후보가 없으면 기존 스트릭은 그대로 둠(최근 수정
       — 원시 검출기가 스캔마다 검출/미검출을 오가는 게 흔해서, 빈 스캔마다 리셋하면
       연속 확정 자체가 거의 불가능해짐), 있으면 그 후보 외의 스트릭만 리셋하고 최고점
       후보의 스트릭을 1 증가
     - **스트릭이 확정 기준(연속 프레임 수)에 도달했는지 분기**: 미달이면 대기, 도달하면
       그 원시 id에 락온 확정 + 그 위치로 추종 트랙 갱신
4. 후보 이력(다음 프레임의 유예판정/속도미분에 씀) 갱신
5. **락온 상태일 때만** 전체 트랙과 추종 좌표를 다시 발행 (카메라가 안 보이는 초근접
   구간에서도 갱신이 계속 나가도록 하는 별도 발행 경로 — 락온 안 된 상태에서는 아무 것도
   새로 확정된 게 없으므로 발행 안 함)

## 4. `predictive_avoidance_node` — 예측적 회피

### 트랙 콜백 (융합된 트랙 목록이 올 때마다 반복)
1. **트랙 각각에 대해 반복**: 위치가 있으면 그 트랙 전용 등속도 칼만필터를 갱신(없으면
   새로 생성, 있으면 갱신) — 여기서 쓰는 칼만필터가 `leg_detector_bridge_node`의 정적배경
   판정에 재사용된 바로 그 클래스
2. **오래된 트랙의 칼만 상태 정리** (반복, 일정 시간 갱신 안 된 트랙 상태 삭제)
3. **동작 모드 분기** (파라미터로 선택, 하나만 켜질 수도 둘 다 켜질 수도 있음):
   - **가상 포인트 모드**: 트랙별로 속도가 임계값 미만(거의 정지)이면 건너뜀 → 남은
     트랙은 일정 시간 뒤의 예측 위치를 계산 → 그 주변에 속도에 비례해 반경이 커지는 원형
     가상 포인트들을 생성 → 전부 모아 포인트클라우드로 `<namespace>/vision/
     predicted_obstacle_points` 발행 → **Nav2 voxel_layer가 구독** (단, voxel_layer의
     observation_sources 등록은 이 노드 담당이 아니라 별도 협의 필요 — 미완성 전제)
   - **costmap 파라미터 조정 모드**: tf로 로봇 위치 조회 — **조회 실패 분기**: 실패하면
     접근속도를 0으로 간주 → 성공하면 모든 트랙에 대해 반복하며 로봇 쪽으로의 접근속도
     성분을 계산해 최댓값 선택 → 그 값에 비례해 inflation 반경/비용 계수를 계산(상한
     있음) → **Nav2 local_costmap의 SetParameters 서비스를 비동기 호출** → 응답 콜백에서
     **성공/실패 분기**: 실패하면 경고 로그만 남김 (서비스가 아직 안 떠 있으면 그것도
     경고 후 이번 주기는 건너뜀)

## 5. 조합 시나리오로 본 전체 흐름 (거리별 예시)

1. **원거리** (웹캠만 사람을 봄, 이 저장소 밖의 노드): `reid_tracking_node` 경로 A가 웹캠
   소스로 트랙 생성/유지 → `predictive_avoidance_node`가 감시만 함(정지 상태면 가상
   포인트 생략)
2. **근접 전환** (OAK-D도 같은 사람을 보기 시작): 경로 A가 이번엔 OAK-D 소스로 매칭 →
   **출처 전환 분기**로 첫 프레임만 위치를 블렌딩해 좌표 불연속 완화
3. **초근접 전환** (라이다 다리검출 시작): 경로 B가 재획득 시도 상태로 진입 → 여러 프레임
   동안 스트릭을 쌓다가(원시 검출기 깜빡임이 있어도 다른 후보로 안 바뀌면 스트릭 유지)
   확정 기준 도달 시 락온 → 이후 경로 A는 이 트랙을 더 이상 덮어쓰지 않고, 경로 B가 매
   라이다 스캔마다 계속 갱신 + 발행
4. **락온 중 사람이 카메라 시야에도 다시 잡힘**: 경로 A는 "독립 관측"만 기록(트랙은 안
   건드림) → 경로 B가 매 스캔 이 독립 관측과 라이다 위치를 비교해 스왑 여부 검증 →
   문제없으면 계속 라이다로 추종, 어긋나면(다른 사람과 뒤바뀐 것으로 의심) 락온 해제 후
   경로 B가 다시 처음부터 재획득 시도
5. **사람이 멀어짐**: 라이다 후보가 유예시간 넘게 안 보이면 락온 해제 → 경로 A가 다시
   주도권을 가짐 → 계속 아무 소스에서도 안 보이면 트랙 자체가 정리되고 추종 대상 재선정

## 6. 현재 미완성/한계 (이번 정리 시점 기준)

- **추종 대상 지정이 자리표시자**: 최초 대상은 "가장 먼저 잡힌 트랙"으로 고른다. 제스처나
  웹캠 호출좌표 기반의 실제 지정은 아직 없다. 한 번 정해진 뒤 그 사람을 계속 따라가는
  부분(sticky_follow)은 동작한다.
- **웹캠 경로가 실제로 연결돼 있지 않다**: `reid_tracking_node`는 웹캠 입력을
  `Detection3DArray`(`/vision/webcam/detections_3d`)로 기대하는데, 저장소의 `person_locator`
  패키지는 `geometry_msgs/PointStamped`를 `person/position`으로 발행한다. **스키마·토픽이
  달라 현재 웹캠 경로는 아무도 발행하지 않는 상태**이며, 지금까지의 검증은 OAK-D+라이다
  조합으로만 했다(웹캠 목업이 필요하면 `mock_webcam_publisher_node`가 있다).
- **외형(ReID) 기반 매칭은 구현돼 있으나 기본 꺼짐**: 이 현장 데이터에서 추종 좌표 지표를
  개선하지 못해 껐다. 근거는 `evidence/evidence_reid_embedding_log.txt` 참고.
- **칼만필터/마할라노비스 게이팅도 구현돼 있으나 기본 꺼짐**: 점프는 줄지만 추종 좌표 발행
  커버리지가 함께 떨어지는 맞교환이라 껐다. 근거는
  `evidence/evidence_kalman_mahalanobis_log.txt` 참고.
- **Nav2 목표 발행/실제 접근 거리 정책은 이 패키지 범위 밖**: `target_person_pose`를
  소비해 실제로 로봇을 얼마나 가깝게 세울지 결정하는 노드는 별도이며, 이 저장소는
  좌표 발행까지만 담당한다.
- **위험/낙상 감지 미구현**: 문서상 8번 항목으로, 메인 기능이 아니라는 전제로 아직
  손대지 않음.
- **`predictive_avoidance_node`의 포인트클라우드 모드는 Nav2 쪽 voxel_layer 등록이
  전제**: 등록 여부는 이 저장소가 관리하지 않는 별도 설정이라, 이 모드가 실제 costmap에
  반영되는지는 별도 협의/검증이 필요하다.
- **실시간성은 depth 발행률에 묶여 있다**: RGB는 10Hz인데 depth가 5Hz라 동기화 결과가
  약 4.84Hz다. 연산은 프레임당 약 27ms(기본 구성)로 이론상 37Hz까지 여유가 있으므로,
  10Hz로 올리려면 로봇 쪽 depth 발행률을 올리면 되고 이 패키지 변경은 필요 없다.
